# РЕГЛАМЕНТ РЕЗЕРВНОГО КОПИРОВАНИЯ · ПОЛИМАТ / rtynbirf

- Версия: 1.0, 2026-11-08. Резерв, который не восстанавливался, резервом не считается.

## 1. Норма 3-2-1

- **3** копии состояния: (1) live на GitHub, (2) бандлы в `polimat-hub/vault/`, (3) офлайн-архив
  у Хозяина вне GitHub.
- **2** носителя: облако GitHub и локальный диск/архив Хозяина.
- **1** копия вне площадки: офлайн-архив (сегодня: `polimat-vault-offline-2026-11-08.zip`,
  90 файлов — бандлы + пак).

Прямое следствие: копия в том же аккаунте GitHub (форк, второй репо, каталог) резервом не
считается — у носителя общая точка отказа.

## 2. Что подлежит пломбе

| Событие | Пломба обязательна |
|---|---|
| DELETE любого репо | до удаления |
| Rewrite истории (filter-repo, force-push) | до переписывания |
| MERGE/ABSORB тел | до переноса |
| Массовая замена файлов | до замены |
| Любая операция, после которой откат «руками» сложнее, чем `git push` | до операции |

## 3. Процедура пломбы (одна и та же всегда)

```bash
git clone --mirror https://github.com/rtynbirf/<repo>.git <repo>.git
git -C <repo>.git bundle create <repo>.bundle --all
sha256sum <repo>.bundle >> vault/MANIFEST.sha256
# запись в RESTRUCTURE-LOG.md — ДО операции, свидетельство — после
```

- Бандл кладётся в `vault/`; строка SHA256 — в `vault/MANIFEST.sha256`; запись в журнале
  содержит дату, операцию, объект, путь к бандлу.
- Несколько веток — важный случай: бандл снимает ВСЕ рефы (`--all`), включая неслитые
  ветки вроде `membrane-2026-11-05`. Плоский `git clone` без `--mirror` ветки теряет.

## 4. Восстановление и тест восстановления

```bash
git clone bundle-rumu.bundle восстановленное-имя   # из бандла поднимается полноценный репо
git fsck                                            # целостность объектов
git rev-parse <путь к дереву>                       # tree-хэш сравнить с пломбой
```

- Эталон: `rumu` восстановлен из `bundle-rumu.bundle`; live-дерево main b21e823… совпало
  с пломбой байт в байт. Тот же эталон показал и дыру: восстановили main, а ветку
  `membrane-2026-11-05` не вернули — восстановление считается незаконченным (Ф3).
- **Тест восстановления — ежемесячно:** один случайный бандл разворачивается в чистый каталог,
  `git fsck` + сравнение tree-хэша. Результат — строка в журнале.
- До первого успешного теста восстановления регламент считается не введённым.

## 5. Долговременная архивация

- Публичные репо (23) — Software Heritage, «Save Code Now»: идентификаторы сохранений —
  в журнал. Это независимый от GitHub носитель истории.
- Приватные — только офлайн-архив Хозяина; SH их не принимает, и не надо.
- `release-vault` (кластер А) — шифрованный офсайт-архив ассетов; для тяжёлых артефактов
  это второй носитель после Releases.

## 6. Периодичность

| Событие | Действие |
|---|---|
| Перед каждой деструктивной операцией | пломба (раздел 2) |
| Еженедельно при активной фазе | бандлы всех репо, затронутых за неделю |
| Ежемесячно | тест восстановления (раздел 4) + обновление офлайн-архива |
| Ежеквартально | `verify_architecture.py` по свежему снимку; расхождение — задача, не дискуссия |

## 7. Планируемое окно отката GitHub

Удалённое через API/веб репо GitHub держит в восстановимых 90 дней (Settings →
Deleted repositories). Каждая DELETE-запись журнала фиксирует дату ⇒ дату истечения окна.
После истечения единственный источник — бандлы.
